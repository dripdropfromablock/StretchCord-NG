# StretchCord NG

**Stream 4:3 stretched games to Discord in 16:9 — rebuilt from scratch with a GPU-only video pipeline.**

StretchCord NG is a ground-up performance rebuild of [StretchCord](../Stretched-Cord-main). Same
features, same workflow, same settings file — but the video path never touches the CPU.

---

## What changed vs. the original

### Video: zero CPU copies

| | Original (v2) | NG (v3) |
|---|---|---|
| Frame path | GPU → staging texture → `Map` → `Marshal.Copy` → managed `byte[]` → `WriteableBitmap` upload | GPU → `CopyResource` → `D3DImage` |
| CPU bytes per 1080p frame | ~16 MB (two full copies) | **0** |
| CPU cost at 1080p60 | ~1 GB/s memcpy + GPU stall per frame | ~0 (one GPU copy instruction) |
| Adapter choice | always Windows default | matched to the game's monitor (no cross-GPU copies on laptops) |
| Presentation | per-frame UI-thread bitmap upload | WPF composites the shared texture directly |

The presentation texture is a D3D11 `B8G8R8A8_UNORM` texture created with
`D3D11_RESOURCE_MISC_SHARED`; its shared handle is opened by a headless D3D9Ex device
(the official WPF interop path — `D3DImage` only accepts D3D9Ex surfaces) and WPF composites
it during its normal render pass. Stretch (Fill/Fit) stays in WPF composition.

Measured on a live CS2 1920×1080 session (RTX 5070): **60 fps steady, 50,310/50,315 frames
admitted over 14 minutes, ~16 % of one CPU core for the entire pipeline** (capture + present
+ audio + UI).

### Audio: event-driven capture

The process-loopback capture thread now waits on the WASAPI event handle
(`AUDCLNT_STREAMFLAGS_EVENTCALLBACK`) instead of `Thread.Sleep(5)` polling — no polling
latency floor, no constant wake-ups, with a 100 ms timed-wait fallback for endpoints that
never signal. Playback ring buffer and the auto-mute verification state machine are ported
unchanged.

### Efficiency cores (Intel hybrid CPUs)

On hybrid CPUs (12th-gen Intel and later), Windows' scheduler *prefers P-cores for
high-priority threads* — which would make the stream workers compete with the game.
`Services/CpuTopology.cs` discovers the E-core set (lowest `EfficiencyClass` from
`GetLogicalProcessorInformationEx`) and pins the two streaming workers — the WGC frame
delivery thread and the audio capture thread — to it, so the game keeps every P-core.
Thread priority still orders work within the E-cores.

Measured on an i7-12700 (8 P-cores, 4 E-cores): both workers ran on logical processors
16-19 (`mask 0xF0000`) and frame throughput was identical to the unpinned scheduler
(≈45 fps, matching CS2's own present rate) — the pipeline is GPU-bound, so the E-cores
absorb it for free. The UI thread is never pinned. "Prefer efficiency cores" can be
switched off in the VIDEO section (threads revert to scheduler placement); on uniform
CPUs the option is inert and the log says so.

### Memory

- Frame path allocates nothing per frame — no staging textures, no managed pixel buffers
  (the old build marshalled ~16 MB per frame through the managed heap).
- The shared presentation texture is **released when the stream stops** and recreated on
  the next frame, so nothing per-source is held between runs.
- Audio ring buffer floor reduced from 500 ms to 250 ms of audio.
- Remaining system RAM (~140 MB) is the WPF runtime itself; frames never enter it.
- "Offload to GPU": the entire frame path already runs GPU-resident end to end — capture
  textures, the copy, the presentation surface and the stretch are all GPU operations;
  the D3DImage shared surface is the one cross-API buffer WPF requires.

### Cursor overlay: render-loop driven

The overlay follows `CompositionTarget.Rendering` only while video is visible, instead of an
always-on 16 ms `DispatcherTimer`. Mapping, per-game calibration and diagnostics are ported
verbatim.

### Interop: no more SharpDX

SharpDX (archived 2019) is gone. All D3D11/DXGI/D3D9 interop is generated by
[CsWin32](https://github.com/microsoft/CsWin32) (raw-pointer COM, `allowMarshaling: false`);
the WASAPI/loopback COM surface remains hand-written (proven code).

## Unchanged on purpose

- Window picker with search, icons, minimized-game handling, "remember last game"
- Stream window: pin, F11/Esc monitor-exact fullscreen, borderless resize, aspect lock, auto-hiding chrome
- Per-game pointer calibration (nudge + scale) with per-game persistence
- Audio auto-routing (prefers virtual cables/idle outputs), mute verification with automatic revert
- Settings file: `%LOCALAPPDATA%\StretchCord\settings.json` — **NG reads the same file as v2**, so
  your games, calibration and output device carry over
- Diagnostics report (`log-ng.txt` now, so the two apps don't fight over one log)

## Building

```
.tooling\dotnet\dotnet.exe build StretchCord-NG\StretchCordNG.csproj -c Release
```

Output: `bin\Release\net8.0-windows10.0.22621.0\win-x64\StretchCordNG.exe`
(requires the .NET 8 Desktop Runtime; Windows 10 1903+ for capture, 2004+ for process audio).

CsWin32-generated sources are emitted to `obj/generated` for inspection (`EmitCompilerGeneratedFiles`).

## Layout

```
Capture/
  D3DCaptureDevice.cs    adapter-matched D3D11 device + WinRT IDirect3DDevice
  D3D9Bridge.cs          headless D3D9Ex device; opens D3D11 shared textures as D3D9 surfaces
  VideoCaptureService.cs Windows.Graphics.Capture session (frame-pool recreate, closed events)
  D3DImagePresenter.cs   CopyResource → D3DImage; fps grid pacing; one-frame-in-flight gate
Audio/                   event-driven loopback capture, ring playback, auto-mute routing
Interop/                 CsWin32 wrapper classes
Models/ Services/        settings, log, window enum, cursor mapping, diagnostics (ported)
UI/ ViewModels/          same UI as v2, wired to D3DImage frames
```
